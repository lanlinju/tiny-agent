# 00. 产品决策与 MVP 边界

## 1. 已确认定位

| 决策项 | 当前选择 | 说明 |
| --- | --- | --- |
| 目标用户 | 开发者本地工具 | 这是默认假设，可改；参考 Claude Code / pi 的本地开发体验。 |
| 首个杀手场景 | 文件操作 | MVP 围绕读取、写入、局部编辑、命令辅助建立闭环。 |
| 运行形态 | 本地进程为主 | 这是默认假设，可改；`server` 是本地会话、事件、审批与广播抽象。 |
| 模型接入 | 多家兼容 | 先定义 `LLMProvider` 边界；优先落地 OpenAI-compatible，Anthropic 仅占位。 |
| 前端优先级 | CLI + Web | 阶段 1 同步规划协议边界，真正 UI 可按阶段推进。 |
| 插件系统 | 后置 | 这是默认假设，可改；先记录扩展点和权限模型，不进入阶段 1 实现。 |

## 2. MVP 不做什么

- 不实现完整 IDE 集成。
- 不实现多租户账号、团队空间、云端权限体系。
- 不实现 Anthropic provider，只保留对齐接口的占位计划。
- 不把插件系统作为阶段 1 的运行时能力。
- 不为了“先跑起来”让 `core` 直接调用文件系统、网络或 UI。

## 3. MVP 成功定义

MVP 的最小成功标准不是功能多，而是架构边界稳定：

1. `protocols` 先行，所有跨层数据都有类型与运行时校验。
2. `core` 只处理消息、工具调用结果和事件发射。
3. `server` 是唯一翻译层，负责会话、审批、事件广播和落盘协调。
4. `tools` 只表达真实世界动作，不承载审批策略。
5. `clients` 只渲染事件并发送命令，不保存业务状态。

## 4. 关键风险

| 风险 | 规避方式 |
| --- | --- |
| 早期把 UI 状态写成业务状态 | 所有 UI 显示都从事件派生。 |
| 工具定义混入安全策略 | 审批策略统一放在 `server/approval`。 |
| LLM provider 绑死主循环 | `core` 只依赖 `LLMProvider.chat` 接口。 |
| 事件协议后补导致前后端分叉 | 新能力必须先改 `protocols`，再改生产者和消费者。 |
| 本地工具误操作 | `shell`、`write`、`edit` 默认走审批。 |

## 5. 决策变更规则

任何影响分层、协议、运行形态或安全模型的变更，都必须先更新本文档，再进入实现。
